01

Give command configuration one owner

Strongin-processBehavior reproduced with execution doubles
Files and evidence
  • config/config.py, lines 208 to 226 · AppConfig resolves training and app_env.
  • cli/train.py, lines 33 to 101 and 145 to 153 · The command resolves training again.
  • cli/load.py, lines 57 to 59 · Provisioning loads AppConfig only for logging.
  • training/runner.py, lines 49 to 65 and 98 to 100 · Experiment defaults to local.
  • training/sweep.py, lines 118 to 154 · Sweep does not forward an environment.

Problem

The command interface accepts settings that never reach execution, while a logging-only caller validates unrelated settings.

Solution

Deepen command configuration so its implementation owns resolution once, before the entry point constructs execution dependencies.

  • Locality keeps precedence decisions together.
  • Leverage reaches both command callers.
  • Tests cross the command interface.

Observed behavior

AppConfig resolvesepochs = 7
The CLI passes to Experimentepochs = 100
AppConfig resolvesapp_env = review
The CLI omits environmentExperiment defaults to local

The probe ran the real training entry point with an isolated environment and no .env file. Execution doubles captured its arguments without training or connecting to a database.

Deletion test. Remove the unused resolution path and unrelated startup requirements. Moving both paths into a new function would add no depth.

Tests to change. Extend test_train_cli.py to prove settings reach single runs and sweeps. Check that training settings cannot block the logging-only path in test_load_cli.py.

Adapter discipline. Keep the existing settings-source adapter mechanism. This work does not justify a new configurable command framework.

First decide whether training is deliberately JSON-only. If it is, delete AppConfig.training instead of inventing precedence between environment settings and files.

02

Make run completion own consistency

Worth exploringports & adaptersOne production caller, two adapters
Files and evidence
  • training/ledger.py, lines 80 to 96 · Completion accepts overlapping facts.
  • training/artifact.py, lines 62 to 87 · The manifest already carries provenance and epochs.
  • training/runner.py, lines 158 to 185 · Experiment supplies those facts again.
  • db/run_ledger.py, lines 78 to 115 · The adapter stores each copy independently.
  • tests/test_run_ledger_contract.py, lines 42 to 55 and 205 to 223 · A case supplies conflicting fingerprints.

Problem

The completion interface accepts several accounts of one training run without enforcing agreement.

Solution

Make the completion module own consistency, while each adapter keeps its storage implementation.

  • Locality concentrates completion rules.
  • Leverage covers both ledger adapters.
  • Tests exercise the existing seam.

The existing contract permits disagreement

The different-fingerprints test changes DatasetProvenance but reuses the first fingerprint in its manifest. The in-memory case passed during this review.

The Postgres implementation also stores those inputs independently, as shown by inspection. This review did not run that adapter or demonstrate corrupt production records.

Related meaning to settle. training/data.py, lines 213 to 266 fingerprints raw data but counts selected features. db/run_ledger.py, lines 138 to 164 reuses the first dataset row for that fingerprint.

Deletion test. Remove the caller's obligation to synchronize duplicate facts. A new record that merely holds the same conflicting values adds no depth.

Tests to change. Extend the shared ledger contract with conflicting-fact cases and with different feature selections over the same raw dataset.

Keep this narrow. Experiment is the only production completion caller, and existing manifests allow missing provenance. Do not make older artifacts unloadable.

03

Concentrate Vault settings resolution

Worth exploringmockBootstrap mismatch reproduced
Files and evidence
  • config/config.py, lines 248 to 274 · Bootstrap uses a separate top-level merge.
  • config/config.py, lines 57 to 118 · The settings source creates the client and handles fallback.
  • security/vault.py, lines 31 to 49 and 103 to 130 · Multipass translates responses and failures.
  • tests/test_config.py, lines 21 to 30 and 81 to 122 · StubVault bypasses the SDK translation.

Problem

A shallow bootstrap merge disagrees with final settings resolution, and error handling spans the settings source and Multipass.

Solution

Give the Vault settings module one precedence rule and keep SDK translation and fallback behind its interface.

  • Locality concentrates settings-source behavior.
  • Leverage removes duplicate resolution rules.
  • Tests include SDK response translation.

Observed bootstrap mismatch

Credentials in the environment, mount override in kwargsconfig.vault.enabled = true
The same constructionMultipass never constructed

The isolated probe used placeholder credentials, disabled .env loading, and mocked Multipass. No Vault request occurred.

Deletion test. Delete the competing merge rule and redundant public obligations. Copying Multipass into config.py without narrowing what callers know adds no depth.

Tests to change. Cover nested settings split across sources, then exercise the real settings adapter with SDK-shaped responses rather than only pre-normalized StubVault values.

Adapter discipline. There is one external Vault adapter and a stub, not evidence for several production secret providers.

Fix the merge and test it first. Broader consolidation is optional, and Multipass is publicly exported. Check external consumers before removing its operations.

Keep the depth that already exists

  • ArtifactStore owns staging and publication. Its tests exercise competing writers and process termination. Deleting it would spread publication rules into callers.
  • Experiment.run owns the order of training, evaluation, publication, and recording. Runner tests check the saved model and usable artifacts after ledger failure. Keep this sequence together.
  • Sweep validates combinations before execution and owns failure continuation. Provisioner owns phase normalization, preflight, and execution order. Their size is not evidence of shallow modules.
  • prepare_features has training and inference callers. Removing it would duplicate coercion behavior, not remove complexity.

Do not turn every finding into a refactor

  • ConnectionPool and db_session split session ownership, but current production transaction calls are already concentrated in the ledger adapter. Leave this lower-leverage cleanup out of the first change.
  • prep_scaled.sql, lines 18 to 39 fits statistics across all rows before data.py, lines 237 to 248 splits the dataset. Held-out rows influence preprocessing. This needs a training-semantics investigation, not a generic module extraction. The effect on evaluation metrics was not measured.
