# Gonzo Pit Strategy - Domain Context

This document captures the ubiquitous language of the project. Use these terms exactly as defined in discussions, variable names, and architecture.

## ML and Training Concepts
- **Experiment**: A single execution of a model training process. It encapsulates the full lifecycle: building the architecture, running the training loop, logging metrics to the database, and saving the final Artifact. The lifecycle runs as ordinary sequential code in `Experiment.run()` — evaluate, then save the Artifact, then close the Training Run — so "the Artifact is the model the metrics describe" holds by statement order rather than by Keras callback order (ADR 0002).
- **Training Run**: One in-flight or finished execution of an Experiment, as recorded in the database. Opens before `model.fit` so a run is visible while it is still training, and always reaches a terminal status — `COMPLETED` or `FAILED`, never left `RUNNING`.
- **Run Ledger**: The module that owns everything the database records about a Training Run — the run row, per-epoch Training Metrics, the Model Metadata mirror, and the DatasetVersion link. Its interface is a context manager (`with ledger.run(config) as run:`) yielding a recorder, so a run cannot be left un-terminated. The Protocol lives in `training/ledger.py`; `db/run_ledger.py` holds the Postgres adapter and `tests/fakes.py` the in-memory one. Callers never see a SQLAlchemy Session.
- **Dataset Provenance**: The identity of the data an Experiment trained on — dataset name, Dataset Fingerprint, record count, feature count — travelling together from the TrainingDataSource through `LoadedData` into both the Artifact Manifest and the Run Ledger.
- **Sweep** / **Grid Search**: A formal module that executes a collection of Experiments sequentially or in parallel to explore a hyperparameter space, emitting interim results.
- **Model Metadata**: The relational-database *reporting mirror* of a trained model's Artifact Manifest (hyperparameters, metrics, artifact path). Used for reporting and queries only — never for inference rehydration (see ADR 0002).
- **Artifact**: A self-describing directory produced by training: the model file (`model.keras`) plus the Artifact Manifest. The sole source of truth for inference rehydration; no database call is required to load a model.
- **Artifact Manifest**: The `manifest.json` saved inside an Artifact, carrying everything needed to rehydrate the model — most importantly `feature_names` in training order (the model's input contract), plus target column, training config, and the Dataset Fingerprint.
- **Dataset Fingerprint**: A content hash of a RawDataset (schema, row count, content digest, source query) computed at fetch time. Identifies a DatasetVersion so Experiments record exactly which data they trained on.
- **RawDataset**: The untransformed, raw data fetched from a source (e.g. database, CSV) before any ML-specific feature engineering, NaN filling, or dataset splitting occurs.
- **TrainingDataSource**: The seam at which a `RawDataset` enters the training pipeline, decoupling data extraction from data transformation. Two adapters satisfy it: `DatabaseDataSource` in production and `StubDataSource` in tests.
- **Feature Preparation**: The value-encoding half of the model's input contract (`prepare_features` in `training/data.py`) — object columns coerced to numeric, booleans to integers, NaN filled. Applied identically at training and inference time; applying it in only one place is train/serve skew. The Artifact Manifest fixes *which* columns and their order, Feature Preparation fixes *how* their values are encoded.

## Database Provisioning
- **Provisioning**: Taking a Postgres server from empty to a migrated, loaded `f1db` — the work behind `gonzo-load`. Owned by `db/provisioning.py`, which sits beside the `migrations/` and `init_db.sql` it drives. Three phases, run in order and short-circuiting on failure: **Init**, **Migrate**, **Load**. Distinct from everything downstream: provisioning produces the raw `f1db.*` tables, dbt turns those into the training dataset (ADR 0003), and the Experiment trains on it.
- **Database Target**: Where a Provisioning run points — host, port, database name, schema. Carries no credentials.
- **Admin Role** / **App Role**: The two credential sets Provisioning needs, and they are not interchangeable. The Admin Role creates the database, the schema, and the App Role, and owns migrations; the App Role owns the data and performs the Load. Which phase needs which is part of the interface, not an implementation detail — Init needs both, Migrate needs the Admin Role, Load needs the App Role.
- **Load Plan**: The ordered sequence of Jolpica CSV files and their target tables. The order is foreign-key order, not alphabetical — it is the reason the Load phase works at all, and it is domain knowledge rather than configuration. Every file in the plan is required; a missing one fails the Load, because dbt's lineage needs all of them and a partial load builds cleanly while being silently wrong.
- **Load Report**: What a Load returns — rows actually written per table. Row counts are the verification that means something here: `psql` exits 0 on a failed `\copy` unless `ON_ERROR_STOP=1` is set, so a silent zero-row load once reported success. Performing the Load in-process (`COPY` via psycopg2) makes that failure raise instead, and the Load Report makes the result checkable without a follow-up query.

## Configuration
- **Environment**: The deployment context of the application (e.g., `development`, `testing`, `production`). Determines behavior like logging verbosity and Vault paths.
- **AppConfig**: The single, unified, strongly-typed configuration tree for the entire application, hydrated via Environment Variables and Vault secrets.
- **Vault Settings Source**: An adapter that transparently bridges HashiCorp Vault secrets into the AppConfig tree during application startup.
